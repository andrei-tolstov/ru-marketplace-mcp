# Руководство по запуску Chrome Head с CDP для MCP

В данном документе описана архитектура, процедура развертывания, подключение и эксплуатация сервиса **Chrome Head с поддержкой Chrome DevTools Protocol (CDP)**, расположенного на сервере `192.168.50.38` в каталоге `/opt/chrome_for_mcp/`.

---

## 1. Назначение и архитектура

### Почему Head (с GUI), а не Headless?
Большинство российских и зарубежных маркетплейсов (Wildberries, Ozon, Avito, DNS, Citilink, Drom, AliExpress) используют современные антибот-системы (Qrator, Cloudflare Turnstile, x5sec, ServiceWorker защиты). Стандартный headless-режим Chromium быстро идентифицируется антибот-фильтрами (флаги `navigator.webdriver`, отсутствие рендеринга окна, фингерпринт движка).

Решение на базе **LinuxServer Webtop (XFCE Alpine + Selkies)** запускает полноценный («живой») графический Chromium внутри виртуального дисплея X11 (Xvfb), предоставляя одновременно:
1. **CDP-интерфейс** на порту `9222` для автоматизированных запросов коннекторов MCP.
2. **Web-доступ к графическому рабочему столу** по HTTPS (порт `3001`) для оператора, позволяющий вручную пройти капчу, решить Cloudflare/Qrator челлендж или авторизоваться.
3. **Общий постоянный том (volume)** `/chrome-profile`, в котором сохраняются сессионные cookies, токены авторизации и пройденные антибот-проверки.

### Архитектурная схема

```
┌──────────────────────── Контейнер webtop-cdp ────────────────────────┐
│                                                                      │
│  XFCE X11 Session (Xvfb :1, софтверный рендеринг CPU)                │
│    └─ Chromium 156 (Head, графическое окно в рабочем столе)          │
│         ├─ --user-data-dir=/chrome-profile                           │
│         └─ --remote-debugging-port=9223 (слушает loopback)          │
│                                                                      │
│  s6-сервис cdp: socat TCP-LISTEN:9222 → 127.0.0.1:9223               │
│  Selkies (Webtop Desktop): HTTPS-прокси на порту 3001 (Basic Auth)   │
└───────────────────────────────────┬──────────────────────────────────┘
                                    │
                                    ▼
┌──────────────────────── Хост (192.168.50.38) ────────────────────────┐
│                                                                      │
│  127.0.0.1:9222:9222 ──> CDP для локальных/туннелированных MCP       │
│  0.0.0.0:3001:3001   ──> Веб-доступ к рабочему столу в LAN           │
│  Docker volume: chrome-profile (/chrome-profile)                     │
└──────────────────────────────────────────────────────────────────────┘
```

> [!NOTE]
> **Особенность Chromium ≥137**: браузер принудительно открывает порт отладки только на loopback (`127.0.0.1`), игнорируя параметр `--remote-debugging-address`. В контейнере запущен `socat`, пробрасывающий входящий порт `9222` на локальный порт Chromium `9223`.

## 2. Структура каталога `/opt/chrome_for_mcp/`

На сервере `192.168.50.38` каталог `/opt/chrome_for_mcp/` содержит:

| Файл / Каталог | Описание |
|---|---|
| `docker-compose.yml` | Основной конфигурационный файл сервиса `webtop-cdp` с лимитами ресурсов, портами и монтированием томов |
| `Dockerfile.webtop` | Dockerfile на базе `lscr.io/linuxserver/webtop:latest` с установкой `socat` и регистрацией s6-сервиса `cdp` |
| `s6/cdp/run` | Скрипт инициализации s6: сброс Singleton-локов, ожидание сокета Xvfb `:1`, запуск Chromium и socat |
| `s6/cdp/finish` | Скрипт завершения сервиса s6 |
| `s6/cdp/type` | Тип сервиса s6 (`longrun`) |
| `README.md` | Детальная техническая документация инфраструктуры Webtop CDP на сервере |
| `PROBE_NOTES.md` | Результаты исследования окружения Webtop (X11, display, PUID, видеоадаптеры) |
| `docker-compose.old.yml` | Резервный compose-файл для минималистичного headless-контейнера на Debian trixie |
| `Dockerfile` | Резервный Dockerfile для минималистичного headless-контейнера |

## 3. Развертывание и запуск на сервере

### 3.1. Подключение к серверу
Подключение выполняется по SSH с использованием ключа:
```bash
ssh -i "C:\Users\andrei\.gemini\id_ed25519_user_root" root@192.168.50.38
```

### 3.2. Запуск контейнера
Перейдите в каталог проекта и запустите сборку и старт сервиса в фоновом режиме:
```bash
cd /opt/chrome_for_mcp
docker compose up -d --build
```

### 3.3. Проверка статуса
```bash
docker compose ps
```
Контейнер `webtop-cdp` должен находиться в статусе `Up (healthy)`. Встроенный healthcheck выполняет проверку доступности CDP каждые 15 секунд через `curl -sf http://127.0.0.1:9222/json/version`.

Просмотр логов:
```bash
docker compose logs -f webtop-cdp
```

### 3.4. Проверка доступности CDP локально на сервере
```bash
curl -s http://127.0.0.1:9222/json/version
```
Ответ должен содержать JSON с версией браузера:
```json
{
   "Browser": "Chrome/156.0.8078.79",
   "Protocol-Version": "1.3",
   "User-Agent": "Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 ...",
   "webSocketDebuggerUrl": "ws://127.0.0.1:9222/devtools/browser/..."
}
```
> [!IMPORTANT]
> Обратите внимание, что в поле `Browser` указан полноценный `Chrome/156...`, а не `HeadlessChrome`.

## 4. Подключение MCP к Chrome CDP

### 4.1. Сценарий А: MCP сервер работает на том же хосте (192.168.50.38)
Если MCP коннекторы запущены локально на том же сервере, настройки по умолчанию в `packages/mcp-core/src/mcp_core/transport/chrome_cdp.py` уже соответствуют портам:
- `CHROME_CDP_HOST=127.0.0.1`
- `CHROME_CDP_PORT=9222`

Дополнительных настроек не требуется.

### 4.2. Сценарий Б: MCP сервер работает на удаленной машине (Windows / локальный ПК)
Порт `9222` на хосте привязан исключительно к `127.0.0.1` в целях безопасности (CDP не имеет встроенной аутентификации). Для подключения удаленного MCP сервера рекомендуется использовать безопасный SSH-туннель.

#### Запуск туннеля из PowerShell (Windows):
```powershell
ssh -N -L 9222:127.0.0.1:9222 root@192.168.50.38 -i "C:\Users\andrei\.gemini\id_ed25519_user_root"
```
После запуска туннеля локальный MCP сервер на вашей машине обращается к `127.0.0.1:9222` прозрачно, как если бы браузер работал локально:
```powershell
curl http://127.0.0.1:9222/json/version
```

#### Альтернатива: Прямой доступ через локальную сеть (LAN)
Если сеть `192.168.50.0/24` полностью доверенная и требуется прямой доступ без SSH-туннеля, в `/opt/chrome_for_mcp/docker-compose.yml` на сервере можно изменить привязку порта:
```yaml
    ports:
      - 3001:3001
      - 192.168.50.38:9222:9222   # вместо 127.0.0.1:9222:9222
```
После перезапуска (`docker compose up -d`) в конфигурации окружения MCP сервера задаются переменные:
```bash
export CHROME_CDP_HOST=192.168.50.38
export CHROME_CDP_PORT=9222
```

## 5. Доступ к графическому интерфейсу (Webtop) и решение капч

Если MCP-коннектор возвращает ошибку `challenge_required` или срабатывает блокировка маркетплейса, оператор может открыть браузер в графическом интерфейсе и решить проблему вручную.

### 5.1. Вход в веб-интерфейс
Откройте в браузере:
```
https://192.168.50.38:3001/
```
- **Сертификат**: Selkies использует самоподписанный SSL-сертификат — подтвердите исключение безопасности в браузере.
- **Аутентификация (HTTP Basic Auth)**:
  - **Логин**: `mcp`
  - **Пароль**: `qRQAvxl65LIjylKK`

### 5.2. Прохождение капчи и авторизации
1. На открывшемся рабочем столе XFCE найдите окно запущенного Chromium (либо откройте его через иконку).
2. Перейдите на проблемный маркетплейс (например, `https://baza.drom.ru/`, `https://www.dns-shop.ru/`, `https://www.citilink.ru/`, `https://www.avito.ru/`).
3. Пройдите интерактивную капчу (слайдер, выбор картинок, Cloudflare Turnstile, Qrator) или выполните вход в аккаунт.
4. После успешного входа все cookies, токены и разрешения сохраняются в постоянный volume `chrome-profile`.
5. Повторите запрос через MCP инструмент — запрос выполнится успешно с использованием обновленной сессии.

### 5.3. Быстрый «прогрев» без открытия GUI (для JS-челленджей)
Для систем вроде Qrator или x5sec часто достаточно разового перехода на главную страницу, чтобы получить валидный токен:
```bash
curl -X PUT "http://127.0.0.1:9222/json/new?https://www.dns-shop.ru/"
```
Через 10–20 секунд маркетплейс выдаст куки в фоновом режиме, после чего можно повторить вызов MCP.

## 6. Важные особенности и безопасность

1. **Singleton-блокировки Chromium**:
   При аварийном завершении контейнера Chromium оставляет файлы `/chrome-profile/SingletonLock` и `SingletonSocket`, содержащие hostname. В compose задан фиксированный параметр `hostname: webtop-cdp`, а скрипт `s6/cdp/run` автоматически удаляет устаревшие файлы блокировки перед запуском, предотвращая ошибки вида *"Profile in use by another computer"*.
2. **Лимиты ресурсов**:
   В `docker-compose.yml` заданы жесткие лимиты:
   - Память: `2g` (в состоянии покоя контейнер потребляет ~400–500 МБ).
   - CPU: `2.0` ядра.
   - Раздел `/dev/shm`: `1gb` (необходимо Chromium для стабильного рендеринга сложных DOM-деревьев).
3. **Сетевая политика (Egress)**:
   Chromium в данном контейнере работает **напрямую с публичного IP-адреса хоста**. Внешние прокси (например, сторонние socks5) намеренно отключены, так как выходные иностранные IP приводят к блокировкам на российских сервисах.

## 7. Диагностика и команды обслуживания

### Проверка состояния сервиса внутри контейнера
```bash
# Статус сервиса cdp в s6 overlay
docker exec webtop-cdp s6-svstat /run/service/cdp

# Перезапуск сервиса cdp без рестарта контейнера
docker exec webtop-cdp s6-rc -u change cdp
```

### Перезапуск всего контейнера
```bash
cd /opt/chrome_for_mcp && docker compose restart
```

### Полная пересборка (с сохранением профиля и cookies)
```bash
cd /opt/chrome_for_mcp
docker compose down
docker compose up -d --build
```
> [!CAUTION]
> Команда `docker compose down -v` удалит том `chrome-profile` со всеми сохраненными сессиями и куками. Используйте флаг `-v` только если требуется полностью сбросить профиль браузера к заводскому состоянию.
